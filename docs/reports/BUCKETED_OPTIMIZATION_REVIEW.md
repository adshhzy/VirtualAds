# Bucketed 缓存与采样优化复核

> 目录迁移说明（2026-10-23）：本文的版本、数值、源码文件名和直接 Python 命令保留当时记录；旧快照仍是平铺目录。当前源码按功能分目录，源码名及启动命令映射见 [目录与迁移指南](../PROJECT_LAYOUT.md)。现有 `scripts/run.ps1` 子命令不变；复跑当前源码时从仓库根目录运行。原始测量 artifact 不随仓库分发。

本轮修复可选 `bucketed` 路径的两项问题：动态布局导致素材重复打包，以及其 PyTorch 采样与默认 `batch` 的 Triton 采样存在 FP32 舍入差异。版本为 `2026-10-21-perf4.4-bucketed`；对照基线是 `9c6e9303a87a25a68a2d999c58afa44784074955`。默认 `batch`、既有分块策略和同步独立 NumPy 接口保持不变。

108 场景筛选、7 个代表场景长测及 1 次独立静态复测已完成。新 bucketed 与当前 batch 在全部已检查帧状态中零差，动态素材桶重打包也已消除；但完整调用未稳定超过当前 `batch_auto`，因此**保留默认 batch 和既有分块表，不新增自动 bucketed 切换**。相对旧 bucketed 的改善因场景而异，部分 mean 或 P95 回退。筛选由首轮 94 个完整场景与同配置补测的 14 个组成，首轮原生异常及证据限制在下文保留。

## 修改范围与数值根因

### 素材打包与布局缓存解耦

`PasteBatchAdapter._prepare_bucket_inputs` 仍按 bbox、实际画布尺寸、设备、素材尺寸和 `area_caps` 更新布局/LUT；素材桶的二次缓存改为由 `_asset_key` 与**有序桶成员**决定。`_asset_key` 已包含素材身份、版本、B、设备、有效尺寸及顺序等信息。

因此，bbox 平移、ROI 改形、容量变化等操作只要不改变有序分组，就复用已经堆叠的素材桶。分组成员变化、B 变化、素材对象替换、版本更新、顺序或源尺寸变化，以及显式 `invalidate_assets()`，仍按需要重新打包。`cache_ads=False` 或版本为 `None` 时仍每帧保守重建。grid 和透明度始终按当前调用打包，原地修改不会被缓存隐藏。

这次只分离了素材打包缓存与布局缓存。动态 bbox 仍会在 CPU 构建稠密 LUT 并传到设备，仍有每帧 grid/透明度打包、patch 拼接和全画布 gather；并未实现 ROI 合并或消除这些开销。

### 复用 batch 的采样算术

旧 `bucketed` 路径在桶内使用 `torch.nn.functional.grid_sample`；`batch` 的加速路径使用 `_warp_paste`。两者的双线性采样数学目标相同，但浮点执行顺序会产生微小差异，少量最终像素恰好跨过 uint8 转换边界。该差异是原可选路径已有的行为，不是本轮缓存修改引入。

固定 seed `24680`、B8、16 个广告位、三种素材尺寸、1080p、9×9 可分离核的诊断如下。首两个 bbox 重合，保留覆盖顺序检验。

| 帧 step | 修改前 canvas 最大绝对差 | 修改前 uint8 不同通道值数 / 最大差 | 修改后 canvas / uint8 最大差 |
| --- | ---: | ---: | ---: |
| 0 | 0.0032196045 | 5 / 1 | 0 / 0 |
| 1 | 0.0036392212 | 9 / 1 | 0 / 0 |
| 7 | 0.0031433105 | 4 / 1 | 0 / 0 |

单广告位诊断中，PyTorch `grid_sample` 与显式分步 FP32 采样最大差为 `0.001708984375`；Triton patch 与相同 FP32 顺序的显式采样/alpha 结果逐位相同。这将差异定位到采样舍入顺序，未通过调阈值、改颜色或改变 blur 来掩盖差异。证据见 `results/bucketed_rounding_before_b8s16.json` 与 `results/bucketed_rounding_after_b8s16.json`。

新增 `warp_bucket_patches` 将 `[B,M,4,h,w]` 的 B、桶成员 M 展平，grid 转为 `[B*M,1,L,2]`，直接调用现有 `warp_paste_into` / `_warp_paste`，每桶一次启动，输出 `[B,M,4,L]`。可用的 Triton `zeros`/`border` 路径由此共享 batch 的采样和 alpha 运算；eager / `reflection` 保留原 PyTorch 路径。后续 palette、覆盖顺序、畸变、模糊、融合及 NumPy 输出仍沿原流程。

以 `9c6e930` 为基线，`_four_samples`、`_warp_paste`、`warp_paste_into`、`paste_gpu_batch`、`_finish_canvas`、`_blend_canvas_eager`、`_blur_canvas_torch` 的 AST 全部相同，证据见 `results/batch_math_unchanged_ast.json`。修复使新 bucketed 对齐当前默认 batch；不能据此声称新 bucketed 与旧 bucketed 的所有 uint8 像素相同。

## 正确性与缓存合同

`check_backend_contracts.py` 的 CPU 检查通过 8 个独立布局 oracle 与 77 个图像比较；CUDA 以 `--max-uint8-diff 0` 通过同样 8 个布局检查及 115 个图像比较，全部逐字节相同。GPU 报告为 `results/bucketed_contracts_gpu.json`，CPU 报告为 `results/backend_contracts_cache_cpu.json`。

检查覆盖透明后置广告位的覆盖语义、重叠、不同实际素材/ROI 尺寸、共享及逐 B grid/opacity、不同采样对齐与 padding、legacy/corrected alpha、dense/separable blur。新增缓存合同同时验证复用和必要失效，不依赖缓存 key 的具体序列化形式：

- 平移、ROI 改形，以及容量改变但分组不变时，素材桶对象继续复用，输出与新建适配器一致。
- ROI 跨容量边界改变分组，以及两个同形状桶交换成员时，重新打包并保持正确素材顺序。
- 素材 identity/revision/尺寸/slot 顺序、B3→B1、显式失效均正确重建；关闭缓存或缺失版本时不复用。
- grid / opacity 原地修改立即影响当前帧；之前返回的 NumPy 数组不被覆盖，也不与新输出共享存储。
- 已复现旧版差 1 级的 1080p fixture 纳入固定回归，dense 与 separable 各检查 step 0/1/7，始终要求零容差。

另有 64 组 bucket patch 边界检查，以及 20 组旧 batch / eager / reflection 不变检查，见 `results/bucket_kernel_edges.json`。检查脚本覆盖 B/M、对齐、zeros/border、alpha 模式、opacity 广播及非连续输入。Ruff 与 Python 3.9 AST 检查通过；这些结果只证明已测输入，不能代替真实业务素材和生产回调验证。

## 同进程性能对照口径

五个候选使用相同的当前 fixture 和计时器，各自持有独立 builder / adapter / camera 状态：

| 候选 | 含义 |
| --- | --- |
| `batch_whole` | 当前 batch，关闭分块 |
| `batch_auto` | 当前默认 batch，查询既有自动分块表 |
| `batch_c4` | 当前 batch，显式分块 4 |
| `before_bucketed` | 隔离加载 `9c6e930` 的旧 builder / adapter / runtime，使用旧 bucketed |
| `bucketed` | 本轮缓存解耦和同算术采样的 bucketed |

`before_bucketed` 来自保留目录 `results/baseline_bucketed_9c6e930`，不是模拟旧模式的开关。收益必须在本轮同进程结果之间计算，不能拿前轮报告的耗时相减。自动启用资格还必须比较当前 `batch_auto`，仅优于旧 bucketed 不足以切换默认。

筛选矩阵是 B=`1,4,8,16` × slots=`4,16,32` × 源尺寸 profile=`one,two,three` × 布局=`static,translate,resize`，共 108 个场景。源尺寸依序为 200×200、500×500、300×600；画布 1920×1080，核 9×9，separable blur，连续 sigma，legacy normalization / camera policy，seed `24680`。输入为合成素材、相机和业务回调，不含视频解码、编码、发送。

本机为 NVIDIA GeForce RTX 4090、Python 3.12.14、PyTorch 2.9.1+cu128 / CUDA 12.8、triton-windows 3.5.1.post24（模块 3.5.1），不能直接外推到不同硬件或用户的其他 Python / PyTorch 组合。

每场景 5 轮，候选轮换顺序，每路径每轮预热 8 次、计时 10 次，合计每路径 50 个样本。mean/P95 由全部 50 个原始 wall 样本计算。未锁定 GPU 频率，也未更改系统电源设置；运行期间观察到设备自适应频率/功耗状态变化，短样本耗时会波动。该轮用于筛选，不以微小差值、极值或单轮结果宣称稳定收益；策略变更还需有代表性的更长复测。

主计时从共享参数准备进入，到可立即读取的独立 NumPy 输出完成，包含当次需要的素材收集与打包、grid/透明度打包、布局/LUT 构建与上传、GPU 计算和输出复制/等待。fixture 输入更新和初次 GPU 素材创建在计时外；计时前后同步设备，各候选持有上一份输出直至本次返回。计时区间内没有 profiler 包装函数。

`--check-timed-steps` 在**独立正确性 pass** 中检查 step `0,1,7,8..17`，覆盖所有计时使用的 13 个不同帧状态；并非在每次计时调用内部计算图像差。当前四候选（whole/auto/c4/new bucketed）要求零容差；旧 bucketed 保留最大 1 级差的诊断，不将其算为 exact。测试另检查输出布局、类型及结果生命周期。

布局重建与素材重打包计数在完整调用后读取对象变化；本轮关注“动态布局仍重建，素材是否减少重打包”的实际计数。显存项是**进程级**口径，包含其他候选的常驻缓存，不能当作各路径独占显存。`cold_assets_ms` 是核和当前布局预热后、仅清素材缓存的一次完整调用；它不是 P95，也不用于自动策略准入。

### 原生异常、补测与数据审计

首轮在 2026-10-21 18:22:33 于 94 个场景完整落盘后原生退出：Windows Application Error 1000 记录 NumPy `_multiarray_umath.cp312-win_amd64.pyd` 中的 `0xc0000005`，模块偏移 `0x2a58b9`，没有 Python traceback，检查时也无可用 native stack/dump。最后完整场景为 `B16_S16_two_static`；下一场景尚无完整正确性记录。仅据故障模块不能判定具体操作或根因，也不能将其归为已确定的环境问题。静态检查未发现明确的输出所有权或新 kernel 越界证据，这不等同于排除所有原生错误。完整事件边界保留于 `results/bucketed_native_incident.txt`。

长测主计时中，translate 三场景合计每路径 900 次、resize 一场景 300 次：旧 bucketed 每次重建布局并重打包素材，新 bucketed 每次重建布局但素材重打包为 0。三个静态场景合计 900 次，两种计数均为 0。所有路径的基础素材缓存新增 miss 为 0。

独立诊断按 `0,0,1,7` 四次调用执行。动态场景的新 bucketed 为 3 次 layout / 1 次素材 pack，旧路径为 3 次 layout / 3 次素材 pack；两者仍有 4 次 grid 和 4 次 opacity pack。B8/S16/three/translate 的新路径中，重复 step 0 的 `prepare_cpu_ms` 为 1.921 ms，而动态 step 1/7 为 21.486 / 21.511 ms。这支持继续优先减少动态布局的 CPU 准备开销。`prepare_cuda_ms` 的事件区间也包含 CPU 调度等待，不能将约 21 ms 全部归为 GPU 内核耗时；诊断单次阶段值不相加替代主计时。
